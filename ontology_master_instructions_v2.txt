SECOND-PASS ONTOLOGY REVIEW, CLEANUP, AND METADATA ENRICHMENT INSTRUCTIONS

PROJECT PURPOSE

This project is building a unified pathology ontology from multiple pathology sources, including WHO-style classifications, Pathology Outlines/textbook-style organization, organ-specific JSON source files, organ-system YAML files, and external terminology/metadata resources.

The current goal is NOT to rebuild the ontology from scratch.

The working ontology already exists in MergeFinalDraft2. This second pass should:
1. manually review and improve the existing hierarchy;
2. resolve obvious within-site duplicates and synonyms;
3. preserve clinically meaningful distinctions;
4. attach useful metadata and external terminology mappings;
5. preserve source provenance;
6. flag genuinely uncertain decisions rather than forcing them;
7. iteratively refine the ontology organ system by organ system.

The ontology should become more clinically coherent without losing useful information from the original sources.

================================================================================
1. FILE / FOLDER ROLES
================================================================================

Use the project folders as follows.

MergeFinalDraft2/
- This is the current best merged ontology.
- Start from this version.
- Do NOT discard it and independently rebuild the ontology from the YAML or JSON source files.
- Treat it as the working draft to be reviewed and improved.

Yaml Files/
- These contain original source hierarchy information organized by organ system.
- Use them to understand how diagnoses were originally grouped and to compare hierarchy differences when needed.
- The YAML hierarchy is evidence, not an unquestionable template.

Source JSON folders/
- JSON files are grouped by organ system.
- Individual JSON files generally correspond to individual organs/sites.
- Use these to inspect source diagnoses, labels, links, aliases, and other source-specific metadata.

Metadata/
- This folder contains the structured external terminology resources used for metadata enrichment.
- Current expected subfolders are:
  - ICD-9/
  - ICD-10/
  - ICD-11/
  - ICD-O3.2/
  - ICD-O4/
  - NCIt/
  - SNOMED (currently empty/unavailable)
- Files may be Excel workbooks, tabular text files, code-description files, annexes, or README/documentation files.
- Before using an unfamiliar metadata file, inspect its README/documentation, sheet names, columns, code fields, version information, and table purpose.
- Prefer these structured local resources over free-form web searching.
- Do not invent metadata that is not supported by a reliable source.
- If multiple terminology versions are present, preserve the terminology system and version in the mapping.
- Do not treat absence of a mapping in one code system as an ontology error. Not every pathology diagnosis will map cleanly or uniquely to every external terminology.

Site Review Instructions/
- Each organ system may have a separate reviewer-feedback file.
- Read the relevant site-specific feedback file before beginning that organ system.
- These reviewer notes identify known problem areas but are NOT exhaustive.
- They do not replace the requirement to inspect every diagnosis and hierarchy manually.

Results/
- Save all modified ontology files, review outputs, and change logs here.
- Never overwrite MergeFinalDraft2 or the original source files.

================================================================================
2. CORE REVIEW PHILOSOPHY
================================================================================

This is a MANUAL REASONING task, not a string-matching cleanup task.

For every diagnosis or assignable entity:
- inspect the diagnosis name;
- inspect the full parent chain;
- determine what the entity actually represents;
- compare it to neighboring diagnoses;
- check whether its current classification makes clinical sense;
- inspect relevant YAML/JSON source entries when needed;
- inspect external metadata resources when needed;
- decide whether its current placement is defensible.

Do not simply preserve hierarchy because it came from a source.

Do not make decisions solely from:
- exact string matching;
- shared keywords;
- prefixes/suffixes;
- embedding similarity;
- fuzzy-match scores;
- automated text similarity;
- the fact that two concepts appear near each other in a source.

Automated searching may be used to FIND possible duplicates, synonyms, source matches, or related records.

The final decision must be based on the concepts' meanings.

The ontology should be reviewed concept-by-concept and branch-by-branch.

================================================================================
3. DECISION PRIORITY
================================================================================

When classification choices conflict, use this priority:

1. Diagnostic correctness
2. Clinically meaningful organization
3. Correct concept identity and synonym handling
4. Preservation of source metadata and provenance
5. Internal consistency of hierarchy
6. Avoidance of redundant nodes
7. Faithfulness to source hierarchy

The original source hierarchy is evidence, not authority.

================================================================================
4. MANUALLY REVIEW EVERY DIAGNOSIS AND ITS PLACEMENT
================================================================================

For every diagnosis/leaf, inspect the complete parent chain and ask:

- Is this diagnosis actually a member of this organ/site?
- Is it neoplastic, non-neoplastic, precursor, tumor-like, benign, borderline, uncertain behavior, in situ, malignant, etc., as claimed by its parent?
- Does it belong to the stated histologic family?
- Is it epithelial, mesenchymal, neuroendocrine, hematolymphoid, germ cell, melanocytic, trophoblastic, etc.?
- Is the parent category clinically meaningful or just inherited from textbook/source formatting?
- Does the diagnosis belong more naturally somewhere else?
- Is the diagnosis being forced into a category simply because one source grouped it that way?
- Is this node actually a diagnosis, or only a grouping/category heading?
- Is the same diagnosis duplicated elsewhere within the same individual organ/site?

If a diagnosis is clearly misplaced, move it to the most defensible location.

If classification is genuinely ambiguous, preserve the diagnosis and FLAG FOR REVIEW rather than making a destructive or speculative change.

================================================================================
5. ORGANIZATION: NEOPLASTIC VS NON-NEOPLASTIC, HISTOGENESIS, BEHAVIOR
================================================================================

The merged ontology sometimes combines different classification strategies because WHO and Pathology Outlines may organize the same site differently.

One source may organize primarily by histogenesis/lineage:
- epithelial
- glandular
- squamous
- mesenchymal
- neuroendocrine
- hematolymphoid
- germ cell
- melanocytic
- trophoblastic

Another may organize primarily by behavior or conceptual status:
- benign
- borderline/intermediate
- uncertain behavior
- in situ
- malignant
- precursor
- tumor-like
- non-neoplastic

These axes overlap. A diagnosis can be both epithelial AND malignant, for example.

Do NOT mechanically preserve both source hierarchies if doing so creates duplicate or overlapping branches.

For every organ/site, manually decide which organizational axis is most informative for each local branch. There is no universal rule that histogenesis must always come first or that benign/malignant must always come first.

Ask:
- Which axis provides the clearest clinically meaningful grouping for this site?
- Are benign and malignant diagnoses being separated in a useful way, or are they needlessly splitting the same histologic family across parallel branches?
- Would epithelial/mesenchymal/etc. be a better primary branch, with behavior beneath it or represented as metadata?
- Conversely, is behavior the clinically established organizing principle for this particular site?
- Are some categories duplicated because WHO and Pathology Outlines used different philosophies?
- Does moving a diagnosis into another existing category make every parent label more semantically accurate?
- Is a category technically true but still unhelpful or redundant?

Treat every parent-child edge as the statement:

    "Child is a type/member of Parent."

That statement must be true AND useful.

If a parent says Malignant tumors, every child under it must be malignant.
If a parent says Epithelial tumors, every child under it must be epithelial.
If a parent says Precursor lesions, every child under it must truly be a precursor.
If a parent says Non-neoplastic lesions, every child under it must actually be non-neoplastic.

Do not keep a diagnosis under a semantically false parent merely because one source placed it there.

Example of a structure that should trigger review:

    Tumors -> Benign tumors -> Epithelial tumors -> Diagnosis A
    Tumors -> Epithelial tumors -> Malignant tumors -> Diagnosis B

This might be defensible, but it might also be two source hierarchies pasted together. Inspect the diagnoses and decide which classification axis is more coherent for that site/branch.

Do not flatten clinically meaningful distinctions merely to make every organ look symmetrical. Clinical meaning is more important than cosmetic consistency.

================================================================================
6. REMOVE SOURCE / TEXTBOOK / NAVIGATION ARTIFACTS
================================================================================

The original source material may contain textbook, chapter, webpage, or navigation language such as:
- Introduction
- Overview
- General
- General information
- Classification
- Terminology
- similar non-diagnostic section labels

These are not automatically ontology concepts.

A. STANDALONE SOURCE HEADING
If a node exists only because it was a textbook/webpage heading and is not a diagnosis or meaningful diagnostic category, remove it or flatten through it.

B. ARTIFACT ATTACHED TO A REAL DIAGNOSIS
If a source title is something like:
- "Endometrial carcinoma - general"
- "X tumor: overview"
and the source page actually represents diagnosis X, keep the diagnosis but clean the concept name to the actual diagnosis. Preserve the original source title in provenance if useful.

C. CLEANING REVEALS A DUPLICATE
If removing General/Overview/etc. reveals that the source entry is simply another instance of a diagnosis already represented within the same site, do NOT create or retain a second leaf. Confirm concept identity and merge its provenance/metadata into the existing diagnosis.

D. DO NOT DELETE THE DIAGNOSIS WITH THE ARTIFACT
A legitimate diagnosis should not be removed merely because its source title contained source-navigation language. Normalize the concept name instead.

Also remove other obviously non-diagnostic navigation/header nodes when discovered.

Concept names should be clean, diagnostic, and free of source-interface wording.

================================================================================
7. DISTINGUISH DIAGNOSIS FROM CATEGORY
================================================================================

Every node should intentionally function as one of:
- a diagnostic entity;
- a meaningful diagnostic grouping/category;
- a cross-reference, if cross-references are used;
- a reserved/placeholder category only when there is an explicit reason.

Do not allow source formatting to turn a diagnosis into a category or a category into a diagnosis.

Avoid structures where an identical diagnosis is unnecessarily repeated beneath a same-named category.

================================================================================
8. WITHIN-SITE DUPLICATE / SYNONYM SCOPE
================================================================================

IMPORTANT: At this stage, ONLY deduplicate within the SAME INDIVIDUAL ORGAN OR SITE.

Examples of individual sites include:
- cervix
- uterine corpus
- ovary
- fallopian tube
- vagina
- vulva
- placenta
- peritoneum
- broad ligament / other uterine ligaments
- other specific organs represented as separate site files

Do NOT currently canonicalize diagnoses across different organs.

Do NOT merge, deduplicate, or cross-link diagnoses merely because the same or similar entity appears in:
- cervix and uterine corpus;
- ovary and fallopian tube;
- different organs within the same organ system;
- different organ systems.

A diagnosis that appears in multiple organs may legitimately remain separately represented for now.

Cross-organ identity reconciliation will be handled later.

This is especially important for:
- neuroendocrine tumors;
- mesenchymal / soft-tissue tumors;
- hematolymphoid lesions;
- metastatic disease;
- melanocytic lesions;
- entities with site-specific criteria or behavior.

Within ONE individual site, however, obvious duplicate leaves, duplicate source-derived copies, alternate spellings, and true synonyms should be reviewed and merged when they genuinely represent the same diagnosis.

================================================================================
9. SYNONYM / DUPLICATE DECISION RULES
================================================================================

Two entries may be merged within an organ/site only when they truly refer to the SAME pathological entity.

Common situations that may represent the same diagnosis include:

A. American vs British spelling
Examples:
- tumor / tumour
- estrogen / oestrogen

B. Punctuation or formatting differences
Examples:
- hyphenation
- capitalization
- minor spacing
- harmless singular/plural formatting where meaning is unchanged

C. Abbreviation vs full name
Only when the abbreviation clearly refers to that exact diagnosis.

D. Explicit synonyms in source material

E. Historical vs current terminology
Only when they genuinely refer to the same entity.
Keep the old/alternate term as an alias.

F. Minor wording differences that do not alter diagnostic meaning
Examples:
- reordered wording;
- implied site term omitted because the site is already established;
- trivial source-specific phrasing differences.

G. WHO vs Pathology Outlines names for the same accepted diagnosis

When merging true synonyms:
1. choose one preferred/canonical display name;
2. retain alternate names as aliases/synonyms;
3. merge all non-conflicting metadata;
4. preserve provenance from all source entries;
5. retain source-original names;
6. retain non-conflicting IDs, links, annotations, and mappings;
7. record conflicts rather than silently discarding them.

DO NOT merge solely because names share important keywords.

Keywords such as:
- carcinoma
- adenocarcinoma
- stromal
- endometrioid
- serous
- clear cell
- squamous
- neuroendocrine
- mesenchymal
- sarcoma
- smooth muscle
- trophoblastic
- germ cell
may occur in many genuinely distinct diagnoses.

DO NOT merge:
- a broad diagnosis with one of its subtypes;
- a tumor family with a specific tumor;
- a precursor lesion with invasive disease;
- benign, borderline, uncertain-behavior, in situ, and malignant forms;
- primary disease with metastatic disease;
- two similarly named site-specific entities when site changes the diagnosis;
- concepts that differ by molecular definition;
- concepts that differ meaningfully in expected behavior or classification criteria.

If names appear synonymous but equivalence is not clear, inspect the source hierarchy, source metadata, and reliable local metadata resources before deciding.

================================================================================
10. SPELLING AND DISPLAY NORMALIZATION
================================================================================

Trivial spelling variants should not create duplicate entities.

Use one consistent preferred display convention in the final ontology.

Preserve source-original wording in provenance and/or aliases where useful.

Do not interpret trivial spelling normalization as evidence that two otherwise different diagnoses are synonymous.

================================================================================
11. PARENT / CHILD RELATIONSHIPS
================================================================================

Do not collapse a broad diagnostic class into one of its subtypes.

If one concept is genuinely broader than another, preserve the parent-child relationship.

Examples of the general pattern:
- broad carcinoma category
  - specific subtype
- broad sarcoma category
  - specific sarcoma type

Do not mark parent and child as synonyms merely because their wording overlaps.

================================================================================
12. REDUNDANT HIERARCHY LEVELS
================================================================================

Look for branches that add no meaningful information.

Examples:
- Borderline Brenner tumor -> Borderline Brenner tumor
- Endometriosis and related conditions -> Endometriosis
  when there are no actual related conditions
- Metastases -> Metastases to ovary
  inside an ovarian ontology

Inspect all single-child categories.

A one-child category is not automatically wrong.

Keep it if it carries real classification meaning.

Flatten it if it is only:
- repeated wording;
- duplicated site wording;
- source-document formatting;
- an empty intermediate heading;
- a meaningless drill-down.

Especially inspect:
- parent and child with effectively identical names;
- empty categories;
- placeholder categories;
- repeated source-derived headings;
- site wording already implied by the organ context.

================================================================================
13. EMPTY AND INCOMPLETE CATEGORIES
================================================================================

Find all non-leaf nodes with:
- zero children;
- only placeholder content;
- a heading implying several diagnoses but only one unexplained child.

Determine whether the category should:
- receive diagnoses currently misplaced elsewhere;
- be intentionally retained;
- be renamed;
- be flattened;
- be removed.

Do not leave misleading empty headings such as Precursor lesions without a concrete reason.

================================================================================
14. METASTASIS BRANCHES
================================================================================

Review metastasis branches carefully.

Do not enumerate every theoretically possible primary cancer that could metastasize to an organ.

Determine whether the ontology intends to represent:
- common metastatic primaries;
- diagnostically characteristic metastatic primaries;
- a limited clinically useful set;
- or a more comprehensive structure.

Use one coherent policy within a site.

Avoid redundant site wording when the organ context already makes it obvious.

Do not create unnecessary deep source-derived hierarchies simply because the original source listed many possibilities.

================================================================================
15. SITE-SPECIFIC DIAGNOSES
================================================================================

Be conservative with site-specific pathology.

Do not over-normalize.

If two entities differ because of:
- organ-specific diagnostic criteria;
- accepted site-specific terminology;
- molecular definition;
- expected behavior;
- classification rules;
- different precursor relationships;
- different site-specific clinical meaning;

keep them separate.

Clinical meaning takes priority over structural neatness.

================================================================================
16. METADATA ATTACHMENT
================================================================================

Metadata enrichment happens only AFTER concept identity has been understood.

Do not attach a code merely because its label looks similar to the ontology diagnosis.

For each diagnosis:
1. resolve the diagnosis identity and preferred name;
2. identify confirmed synonyms/aliases;
3. search structured local metadata resources for candidate mappings;
4. inspect candidate meaning and granularity;
5. decide whether the mapping is exact, broader, narrower, approximate, ambiguous, or absent;
6. attach only mappings that have been semantically verified.

Not every diagnosis should have a mapping in every terminology system.

Missing metadata is preferable to false metadata.

For each diagnosis, attempt to attach where supported:

A. Preferred/default name

B. Synonyms / alternate names

C. Acronyms / abbreviations

D. Source provenance
Preserve:
- source name;
- original source diagnosis/page name;
- original organ/site;
- original hierarchy/path;
- source URL, if available;
- source-specific ID, if available;
- source file name.

E. WHO mapping
Where available:
- WHO preferred/entity name;
- WHO identifier/code;
- WHO source/version;
- WHO link/reference.

F. Pathology Outlines mapping
Where available:
- Pathology Outlines title;
- page/link;
- source path;
- source identifier if present.

G. ICD-9 mapping, when supported

H. ICD-10 mapping, when supported

I. ICD-11 mapping, when supported

J. ICD-O 3.2 mapping, when supported

K. ICD-O 4 mapping, when supported

L. NCIt mapping, when supported

M. SNOMED CT
- CURRENTLY DO NOT POPULATE unless authorized structured SNOMED data is later added to Metadata/.
- The current SNOMED folder is empty/unavailable.
- Do not invent SCTIDs and do not substitute random web results for an authorized terminology source.

N. Other structured metadata resources placed in Metadata/
Include only when they clearly map to the same concept and add useful information.

O. Related terms
Use VERY conservatively. Do not use related_terms as a dumping ground for vaguely associated concepts. Prefer synonym, acronym, parent/child relationship, provenance, or formal external mapping whenever possible.

If no reliable mapping exists, leave the field empty or FLAG FOR REVIEW.

Never invent IDs, codes, synonyms, or links.

================================================================================
17. METADATA TABLE REVIEW AND ITERATIVE MAPPING
================================================================================

Metadata/ currently contains multiple coding systems and file formats.

Before assigning anything from a metadata resource:
1. inspect README/documentation if present;
2. inspect workbook sheet names if Excel;
3. inspect column names;
4. identify the actual code field;
5. identify the preferred label/description field;
6. identify terminology version;
7. determine whether the table is a direct code table, index, annex, order file, morphology table, topography table, or another auxiliary file;
8. identify behavior/topography/morphology fields where applicable.

Do not assume every TXT/XLSX file is a direct diagnosis-to-code lookup.

Use an iterative mapping process:

STEP 1 — GENERATE CANDIDATES
Search using:
- preferred diagnosis name;
- confirmed synonyms;
- acronyms when unambiguous;
- normalized tumor/tumour spelling;
- source-original names.

STEP 2 — VERIFY SEMANTICS
For each candidate ask:
- Is this actually the same disease/entity?
- Is the external concept broader than the ontology diagnosis?
- Is it narrower?
- Is it site-only rather than histology-specific?
- Is it morphology-only?
- Is it a legacy category?
- Does behavior match?
- Does topography match when relevant?

STEP 3 — ASSIGN RELATION
Use:
- EXACT: same diagnosis/entity
- SYNONYM: accepted alternate label for same entity
- BROADER: external code/category is broader than ontology diagnosis
- NARROWER: external concept is more specific
- APPROXIMATE: useful related mapping but not identity
- AMBIGUOUS: multiple plausible mappings / insufficient certainty
- NO_MATCH: no defensible mapping found

Do not call a broad ICD category EXACT merely because it contains the diagnosis.

STEP 4 — ATTACH PROVENANCE
Preserve where possible:
- terminology system;
- version;
- code;
- external preferred label;
- source file;
- source workbook sheet/table;
- mapping relation;
- confidence;
- notes for non-exact mappings.

STEP 5 — RECHECK AFTER ALIASES MERGE
If several internal aliases collapse into one diagnosis, consolidate their external mappings at the canonical diagnosis level. Do not create duplicate mapping records simply because several aliases matched the same external code.

STEP 6 — ITERATE
After the first metadata pass, review ambiguous/no-match diagnoses separately. Use additional synonyms/source names where justified, but do not loosen semantic standards merely to increase coverage.

================================================================================
17A. ICD-O 3.2 / ICD-O 4 RULES
================================================================================

For neoplasms, preserve ICD-O components separately when available:
- ICD-O version;
- morphology code;
- morphology label;
- behavior component/classification;
- topography code;
- topography label;
- mapping relation;
- source file/table.

Do not collapse morphology and topography into one uninterpretable value.

The same morphology code may legitimately occur in multiple organs.
The same external code may legitimately map to multiple ontology diagnoses.
That is not automatically a duplicate or error.

Do not merge ontology diagnoses merely because they share an ICD-O code.

Where both ICD-O 3.2 and ICD-O 4 are available:
- preserve the version explicitly;
- prefer the newer ICD-O4 mapping when applicable for current metadata;
- retain ICD-O3.2 where useful for legacy/version comparison;
- do not silently treat codes from different versions as interchangeable.

================================================================================
17B. ICD-9 / ICD-10 / ICD-11 RULES
================================================================================

General ICD systems may be broader than the pathology ontology and may emphasize site, behavior, or clinical coding rather than detailed histology.

Therefore:
- do not force every pathology diagnosis to have an ICD mapping;
- do not treat a broad site/behavior code as exact histologic identity;
- use BROADER or APPROXIMATE when appropriate;
- preserve terminology version and source file;
- permit multiple diagnoses to share the same ICD code;
- permit one diagnosis to have more than one justified context/version mapping;
- do not merge ontology diagnoses merely because they share an ICD code.

ICD-9 should generally be treated as legacy metadata rather than as a driver of concept identity or hierarchy.

ICD-10 and ICD-11 should supplement the ontology, not determine its structure.

================================================================================
17C. NCIt RULES
================================================================================

Use the structured NCIt files in Metadata/ as the preferred source.

For a verified NCIt mapping preserve:
- NCIt code;
- preferred term;
- useful accepted synonym when relevant;
- mapping relation;
- source/version when available;
- source file/table.

If NCIt contains both a broad family concept and a specific diagnosis, map to the most appropriate level and label the semantic relation correctly.

Do not assign an NCIt code solely because one keyword matches.

================================================================================
17D. SNOMED RULES
================================================================================

SNOMED is not part of the current enrichment pass because the project does not currently have the required structured/authorized SNOMED data.

Leave SNOMED fields empty/unmapped for now.

Do not:
- invent SCTIDs;
- scrape random web pages for SCTIDs;
- treat missing SNOMED data as a quality failure.

If an authorized structured SNOMED dataset is later added to Metadata/, perform a separate SNOMED enrichment pass.

================================================================================
17E. SHARED CODES AND MULTIPLE CODES
================================================================================

It is completely acceptable for multiple diagnoses to share the same external code.

External coding systems may be less granular than this ontology.

Likewise, one diagnosis may legitimately have multiple mappings because of:
- terminology version;
- morphology plus topography;
- behavior;
- legacy coding;
- context-dependent granularity.

Never infer concept identity from code equality alone.

Never merge diagnoses merely because they share a code.

Never create artificial duplicate external mappings because several aliases resolve to the same code.

================================================================================
18. WHO / NEW CLASSIFICATION MATERIAL
================================================================================

A newer WHO-related source or classification material may be added to the project.

For the current pass:
- do NOT automatically rebuild the ontology around newly introduced WHO diagnoses;
- do NOT let a new WHO source destabilize an otherwise coherent second-pass cleanup.

However:
- inspect the new WHO material when relevant to terminology or classification questions;
- note any genuinely new diagnoses not represented in MergeFinalDraft2;
- record them as possible additions for a later dedicated incorporation pass;
- preserve enough information to revisit them later.

New WHO diagnoses should generally be embedded into the ontology in a later deliberate pass after the current cleanup is stable, unless there is a compelling reason to add one immediately.

Maintain a NEW WHO CANDIDATES list containing, where available:
- proposed diagnosis name;
- organ/site;
- source/version;
- source path;
- whether it appears genuinely new versus a rename/synonym;
- possible parent location;
- notes requiring review.

During the later dedicated WHO incorporation pass, compare each candidate against the cleaned ontology before adding it. New source terminology may represent a genuinely new diagnosis, a renamed diagnosis, a reclassified diagnosis, or a synonym. Do not create duplicates merely because a new WHO edition uses a new name.

If a new WHO source clarifies that an existing diagnosis is misnamed, obsolete, or clearly misclassified, record the issue and flag it for review rather than silently restructuring large branches.

================================================================================

When comparing concepts, use the following relationship labels when useful:

SAME_CONCEPT
- genuinely the same pathological entity

SYNONYM
- alternate name for the same entity

PARENT_CHILD

KEEP_SEPARATE

GROUPING_ONLY

NEEDS_REVIEW

================================================================================
21. PROVENANCE PRESERVATION
================================================================================

Structural cleanup must NOT destroy source provenance.

Whenever an entity is:
- merged;
- renamed;
- moved;
- deduplicated;
- flattened;
- remapped;

retain enough information to reconstruct:
- which source(s) contained the entity;
- the original source name;
- original hierarchy/path if useful;
- source-specific IDs/mappings;
- aliases;
- source URL(s);
- source file(s);
- other useful source metadata.

Where an entity appears in multiple sources, combine provenance rather than choosing one source and deleting the other.

================================================================================
22. METADATA CONFLICTS
================================================================================

If two sources disagree:
- do not silently choose one value;
- preserve both source-specific values when useful;
- record the conflict;
- flag the concept if the disagreement affects identity or classification.

If one source is clearly using older terminology for the same established entity, the modern term may be used as preferred name while retaining the older term as an alias.

If disagreement may indicate two genuinely different diagnoses, do NOT merge.

================================================================================
23. MISSING SOURCE CONCEPTS
================================================================================

While reviewing source files, you may encounter concepts not present in MergeFinalDraft2.

Do not automatically insert every missing heading or term.

First determine whether the missing item is:
- a true diagnosis;
- a synonym of an existing diagnosis;
- a parent/grouping category;
- an organizational artifact;
- intentionally represented elsewhere within the same site;
- a genuinely missing diagnosis;
- a new WHO diagnosis better handled in a later incorporation pass.

If genuinely missing and clearly justified, record it as a proposed addition or flagged issue.

Do not quietly insert uncertain entities.

================================================================================
24. ORGAN-LEVEL CONSISTENCY PASS
================================================================================

After manually reviewing individual diagnoses within an organ/site, perform a full organ-level consistency pass.

Check for:
- duplicate canonical entities within the same site;
- synonymous entities not merged;
- contradictory classifications;
- inconsistent benign/borderline/malignant organization;
- inconsistent epithelial/mesenchymal/etc. organization;
- empty branches;
- redundant single-child chains;
- Introduction/Overview/source artifacts;
- repeated categories inherited from multiple sources;
- diagnoses under incompatible parents;
- aliases accidentally represented as separate diagnoses;
- metadata lost during merges;
- duplicate external mappings;
- suspicious naming inconsistencies;
- unsupported metadata mappings.

Do not stop after fixing only the initially obvious examples.

Apply the same reasoning systematically across the full site.

================================================================================
25. DIAGNOSIS COUNTING
================================================================================

When counting diagnoses:

Count:
- distinct diagnosis leaves;
- non-leaf nodes that are themselves valid assignable diagnoses even if more specific children exist beneath them.

Do NOT count:
- pure organizational headings;
- empty grouping nodes;
- source-navigation artifacts;
- aliases/synonyms as separate diagnoses.

================================================================================
28. ITERATIVE REVIEW / REFINEMENT
================================================================================

This project is explicitly iterative.

Do not assume one pass permanently resolves a site.

Work one organ/site at a time using the following loop.

PASS A — ORIENT

32. HISTORICAL VS CURRENT CLASSIFICATION, EXTERNAL VERIFICATION, AND DIAGNOSTIC GRANULARITY
================================================================================

Some organ/site branches cannot be reviewed correctly by comparing only the existing merged ontology, WHO source hierarchy, and Pathology Outlines hierarchy.

Classification systems change over time, and different sources may organize the same diagnostic space using different axes. The ontology may therefore contain:
- older broad diagnostic categories;
- newer more specific diagnoses;
- historical classification systems still useful for legacy data;
- histogenesis/lineage categories such as epithelial, neuroendocrine, mesenchymal, etc.;
- behavior categories such as benign, borderline/intermediate, in situ, malignant, etc.;
- grade, differentiation, severity, chronicity, pattern, or morphology labels;
- broad family labels where current pathology practice would ordinarily report a more specific diagnosis.

For these branches, do NOT simply ask whether the existing source structures were merged correctly.

Also ask whether the source classifications themselves are current, clinically meaningful, sufficiently granular, and compatible with one another.

When necessary, use reliable current pathology references, current classification material, and other authoritative sources to verify:
- what the diagnosis is currently called;
- whether an older term remains current, is historical, is broader, or is a true synonym;
- which subdivisions are currently recognized;
- whether a pathologist would actually sign out the broad label or normally use a more specific diagnosis;
- whether grade/differentiation/severity/chronicity is part of the diagnostic entity or an orthogonal attribute;
- whether two source hierarchies are organizing the same concept space on incompatible axes.

Do not accept WHO or Pathology Outlines organization merely because it is present in the project. Use them as evidence and provenance, then verify the medically appropriate current representation when the hierarchy is unclear or conflicting.

RECONCILING INCOMPATIBLE ORGANIZATIONAL AXES
WHO and Pathology Outlines may organize the same site differently.

For example, one source may primarily divide tumors into:
- epithelial;
- neuroendocrine;
- mesenchymal;
- hematolymphoid;
- germ cell;
- other lineage/histogenesis groups;

while another may primarily divide them into:
- benign;
- borderline/intermediate;
- in situ;
- malignant;
- other behavior categories.

These are overlapping axes, not automatically separate conceptual spaces.

A tumor can be both epithelial and benign.
A tumor can be both neuroendocrine and malignant.
Therefore, do NOT preserve both source schemes as parallel ontology branches merely because each is technically true.

For each affected branch, determine:
1. what concepts each source is trying to distinguish;
2. whether both distinctions are clinically useful;
3. which axis should be primary in the hierarchy;
4. whether the second axis belongs beneath it, belongs in metadata, or is unnecessary as a hierarchy level;
5. whether preserving both would cause the same diagnoses or conceptual families to appear repeatedly under different headings;
6. whether a proposed parent category is true for every child and adds meaningful information.

Avoid needless categories that exist only because a diagnosis could technically fit under them.

Avoid structures where the same conceptual space is independently represented once by behavior and again by lineage, producing duplicate or near-duplicate branches containing different subsets of the same family.

There is no universal rule that lineage must always be primary or that behavior must always be primary.

Make this decision branch by branch based on:
- current accepted classification;
- clinical usefulness;
- diagnostic reporting practice;
- whether the hierarchy remains semantically true;
- whether the organization avoids unnecessary duplication;
- whether historical data can still be represented.

Record the reason for the chosen organization when reconciling substantially different source schemes.

CURRENT DIAGNOSTIC GRANULARITY
Do not assume an existing broad ontology node is sufficiently granular merely because it is technically correct.

For every broad diagnostic family, ask:

    Would a practicing pathologist ordinarily stop at this label,
    or would the final diagnosis normally contain a more specific
    recognized subtype, differentiation, grade, pattern, or other
    diagnostic distinction?

If current practice routinely uses recognized diagnoses below the existing broad node, investigate whether actual diagnoses are missing from the ontology.

This is especially important when:
- the ontology jumps directly from a broad category to a generic leaf;
- sibling branches are represented at much finer diagnostic resolution;
- a physician would ordinarily include a more specific recognized term in the diagnosis;
- distinctions affect accepted nomenclature, prognosis, management, classification, or interpretation;
- the broad source category appears to be a grouping concept rather than the terminal diagnosis.

Use authoritative current references to identify the appropriate recognized diagnoses.

Do not invent subdivisions merely to increase granularity.

Add or propose missing concepts only when they represent real diagnostic terminology that would plausibly appear in pathology reporting.

DISTINGUISH DIAGNOSIS FROM GRADE / SEVERITY / DIFFERENTIATION / CHRONICITY
Terms such as:
- well differentiated;
- moderately differentiated;
- poorly differentiated;
- low grade;
- high grade;
- mild;
- moderate;
- severe;
- acute;
- chronic;

may be clinically important without always representing independent disease entities.

For each disease, determine whether such a term is:
- part of the recognized diagnostic entity;
- a formal subtype;
- a formal grade;
- a differentiation category;
- a severity descriptor;
- a chronicity/state descriptor;
- or another attribute.

Represent the distinction accordingly.

Do not create separate diagnosis leaves for every severity or grade value when these are better represented as attributes.

Conversely, do not collapse genuinely distinct recognized diagnoses into one broad family merely because they share lineage.

HISTORICAL TERMINOLOGY AND LEGACY DATA
The ontology must remain useful for historical datasets even when diagnostic classification has changed.

When older and newer schemes coexist, determine whether each older term is:
- still a current preferred diagnosis;
- a true synonym for a current diagnosis;
- a broader historical category;
- an older classification axis spanning several current diagnoses;
- a legacy coding/reporting category;
- or a concept that remains independently meaningful.

Do not place historical and current terms beside one another as equivalent leaves when they represent different levels or different classification systems.

Preserve historical usefulness through the most appropriate mechanism, such as:
- synonym/alias;
- historical term field;
- BROADER/NARROWER relationship;
- legacy classification metadata;
- meaningful parent category;
- provenance to the original source system.

The goal is to allow historical records to map into the ontology without forcing the current diagnostic hierarchy to reproduce an obsolete classification system.

12. Record the rationale when rejecting or modifying a source hierarchy because another organization is more clinically defensible.

The goal is not to maximize the number of categories or to preserve every source hierarchy simultaneously.
